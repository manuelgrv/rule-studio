## Cabecera y referencias

kind, dsl_version="0.1", definition_id, definition_version, created_by, created_at. Las evaluaciones fijan input_contract con ID, versión y hash SHA-256 del esquema. Constantes, variables, reglas y productos están contenidos en el documento; no se resuelven versiones «latest».

El hash usa JSON con claves ordenadas y separadores compactos, UTF-8 y sin NaN. rm_runs conserva documentos, hashes y versión de biblioteca. Una firma de aprobación no está implementada en esta entrega; eso pertenece a la etapa de workflow.

## Inputs

root identifica alias de fuente y clave de cliente. sources contiene IDs, table_ref y esquema de los campos permitidos; el adaptador resuelve table_ref contra un catálogo explícitamente autorizado. No aceptar nombres de tablas arbitrarios desde el DSL.

joins declara parent, source, left_key, right_key, cardinality (one/many) y order_by. Cada alias tiene un padre; grafo conectado y acíclico. Tablas físicas repetidas requieren alias distintos.

mappings es recursivo:

- ref: source y field; puede incluir join de cardinalidad one para recuperar un escalar.
- object: mapa de campos; join opcional para objeto relacionado 1:1.
- array: mapa de campos de cada objeto y join obligatorio de cardinalidad many.

output_schema declara tipos, nulabilidad, struct.fields y array.items en cada nivel. Los arrays 1:N y sus objetos no son nulos; ausencia genera []. Un objeto/escalar 1:1 ausente puede ser null solo si su esquema lo permite; de otro modo falla la materialización. Múltiples coincidencias 1:1 fallan y revierten la escritura.

El compilador produce SQL con subconsultas correlacionadas y agregaciones LIST ordenadas, evitando el producto cartesiano entre ramas 1:N. Se validan tipos reales del catálogo antes de ejecutar y todos los valores consolidados antes de confirmar.

## Expresiones

Cada nodo tiene exactamente una de estas formas:

```json
{"ref":{"scope":"input","path":["age"]}}
```

```json
{"literal":{"value":18,"data_type":{"type":"integer","nullable":false}}}
```

```json
{"op":"gte","args":[{"ref":{"scope":"input","path":["age"]}},{"literal":{"value":18,"data_type":{"type":"integer","nullable":false}}}]}
```

Scopes: input, variable, constant, rule, local (solo bajo let) e item (solo en predicados de arrays). Productos admiten únicamente referencias a reglas y and/or/not. Variables no referencian reglas; reglas no componen otras reglas directamente.

Operadores: add/sub/mul/div, eq/ne/gt/gte/lt/lte, and/or/not, is_null, coalesce, if, let, sum/count/min/max/mean, exists/all. Agregados numéricos admiten path para acceder a campos de objetos. Predicados reciben un segundo árbol con scope item; se permiten también predicados anidados sobre arrays de objetos.

## Tipos y nulos

integer es entero firmado de 64 bits. decimal admite precisión hasta 28 y escala hasta 6. Literales decimales se serializan como cadenas exactas. Operaciones decimales, división y promedio producen DECIMAL(28,6), con redondeo half-even; overflow es error. No hay casts implícitos que pierdan precisión al persistir valores.

Comparaciones y aritmética propagan null. coalesce requiere tipos iguales y reduce nulabilidad cuando su alternativa no es nullable. Las reglas deben inferirse como Boolean no nulo; la anotación Python no es suficiente. Usar coalesce o is_null explícitamente. No se implementa estrechamiento de tipos por una condición if de nulabilidad.

Arrays vacíos: suma/conteo=0, min/max/promedio=null, exists=false, all=true. Decisión técnica de v0.1: agregados numéricos omiten elementos/campos null; una colección numérica enteramente null equivale a vacía para esos agregados. count cuenta elementos, incluidos null. Un array null propaga null. Predicados deben ser no nulos; no omiten errores de elementos.

Variables virtuales materializadas son escalares (numéricas, booleanas, strings, fechas o timestamps); los arrays/structs permanecen en el input. Fechas/timestamps admiten referencias, literales tipados y comparación; transformaciones temporales y zonas horarias no están implementadas.

## Python y SQL

Python: una función con parámetros inputs, opcionalmente variables y constants en ese orden, y anotación -> bool. Admite referencias por claves literales, comparaciones, aritmética, lógica, asignación local única, if/else y expresión condicional. Todos los caminos deben retornar booleano. Las asignaciones se traducen a let con nombre y dos argumentos (valor, continuación); se evalúan incluso si no se usa la variable, conservando errores y evitando expansión exponencial del árbol.

Sin imports, decoradores, loops, recursión, código dinámico, acceso por atributos, llamadas arbitrarias ni efectos externos. Lambda solo como predicado de exists/forall con un parámetro item. El código se parsea, no se ejecuta.

| Python | SQL | DSL |
| --- | --- | --- |
| sum_values / min_value / max_value / mean_value(array, "campo") | DSL_SUM / DSL_MIN / DSL_MAX / DSL_MEAN(array, 'campo') | sum/min/max/mean + path |
| count_items(array) | DSL_COUNT(array) | count |
| exists(array, lambda item: …) | DSL_EXISTS(array, item.campo > …) | exists |
| forall(array, lambda item: …) | DSL_ALL(array, item.campo > …) | all |
| coalesce(a,b) | COALESCE(a,b) | coalesce |
| x is None / is_null(x) | x IS NULL | is_null |
| a if condición else b | CASE WHEN condición THEN a ELSE b END | if |

SQL acepta una expresión o SELECT de una expresión sin FROM. Se usa SQLGlot para parsear, pero una lista explícita de nodos permitidos determina qué se compila. No se ejecuta SQL de autoría ni se transpila ciegamente. JOINs pertenecen al DSL de inputs, no al de reglas.

No están implementados IN/BETWEEN, funciones generales pandas/PySpark, bucles ni APIs arbitrarias. Rangos se expresan con comparaciones y AND; listas de alternativas con OR. Límites: fuente 32 mil caracteres, AST hasta 1000 nodos y profundidad 60; documentos hasta 20 mil nodos y profundidad 60.

## Ejecución y fallos

EvaluationPlan valida el paquete y ordena variables por dependencia. Solo calcula variables/reglas requeridas por productos seleccionados; evalúa todas esas reglas. if y coalesce son perezosos; and/or y predicados recorren sus operandos para no ocultar errores.

Error de variable → dependencias afectadas con DEPENDENCY_ERROR. Regla fallida → resultado null; productos que la referencian quedan null con RULE_ERROR. Las dependencias independientes continúan. El resultado persistido nullable no habilita return None en autoría.

Tres tablas relacionadas por ejecución e input, con colecciones tipadas de reglas/variables. La traza de variables usa un STRUCT de slots escalares y metadata de tipo; solo el slot correspondiente contiene el valor.

La escritura de las tres salidas y del registro de ejecución es una transacción DuckDB. Una corrida con errores aislables se marca completed_with_errors; fallos globales revierten la transacción. Reintentar mismo ID y solicitud reutiliza resultados; cambiar lógica/input/productos para ese ID produce RUN_ID_CONFLICT.

## Reproducibilidad y límites del adaptador

Fuente sintética fijada con Faker y random, semilla y versiones bloqueadas en uv.lock. No se reemplazan tablas fuente existentes. El consolidado sirve como snapshot local; las tablas locales no son almacenamiento inmutable frente a modificaciones SQL externas.

El motor de evaluación es un intérprete de referencia local, no distribuido. Lee la materialización local en memoria y guarda resultados por lotes tipados. El backend Spark es futuro.

DuckDB no posee partición física de tabla por execution_id: la exportación Parquet demuestra esa partición. El adaptador rechaza cambios incompatibles de schema de un consolidado existente; las migraciones de almacenamiento quedan para una etapa posterior.
